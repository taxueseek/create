# zaoren-process：流程节点分析系统

> 流程出问题，第一反应是换人。但换完人，同样的地方还是断。
> 因为问题不在人，在节点。

`zaoren` 系列其他 skill 造的是「人的判断系统」。`zaoren-process` 造的是「流程节点的断裂模式」——同一个位置，换任何人去做都会出问题的结构性缺陷。

---

## 核心区分

| 人的问题 | 节点问题 |
|---|---|
| 这个人能力不够 | 这个位置上换三个人都出了同样的问题 |
| 他没有认真执行 | 这个步骤的输入条件本身不完整 |
| 沟通不到位 | 两个节点之间没有明确的交接协议 |
| 执行慢 | 这个节点的决策权不清晰，等待成本高 |

**判断依据**：如果同一个问题在不同的执行人手里重复出现，那是节点问题，不是人的问题。

---

## 流程节点的五类断裂模式

### 断裂类型 1：输入不完整
节点收到的信息不足以执行，只能靠猜或者反复确认。

识别标志：
- 「我以为你们会提供……」
- 反复拉回上游确认
- 不同时期的执行质量差异大（因为每次猜的结果不同）

典型场景：需求文档交给工程前缺少关键参数；设计稿交给开发时没有边界情况说明

### 断裂类型 2：交接协议缺失
两个节点之间没有明确的「完成标准」，执行方认为交出去了，接收方认为还没准备好。

识别标志：
- 「我以为你已经在做了」
- 任务在两个节点之间悬空
- 责任边界争议

典型场景：产品说「需求已经给了」，工程说「需求还没确认」；运营说「活动上线了」，设计说「最终稿还没确认」

### 断裂类型 3：决策权模糊
节点到了需要判断的地方，没有人被明确授权做这个判断，导致等待、升级、或者各自做了不同的判断。

识别标志：
- 「我不确定我能不能决定这个」
- 相同情况下不同人给出了不同判断
- 事情做完了才发现判断方向错了

典型场景：紧急情况下谁有权调整预算；客户提了超出范围的需求谁来决定接不接

### 断裂类型 4：反馈回路断裂
执行结果没有回到产生这个任务的决策者，导致同样的错误决策重复出现。

识别标志：
- 「上面不知道实际情况是这样的」
- 复盘总结写了，但下次还是一样
- 问题在执行层解决，没有传递给决策层

典型场景：前线遇到的客户问题没有系统性传递到产品；工程的技术风险判断没有到达项目决策者

### 断裂类型 5：节点超载
一个节点承担了超出其容量的任务，变成瓶颈，整个流程在这里减速。

识别标志：
- 「所有事都要等他/她过」
- 这个节点的在途任务持续积压
- 质量随负载增加而下降

典型场景：一个 PM 同时 review 5 个项目的需求；审批人是唯一签字人，出差就全卡住

## 执行流程

### Step 1：流程速写

让用户描述这个流程的完整路径，不需要很详细，能看出节点就够：

```
起点（谁触发）→ 节点 1 → 节点 2 → ... → 终点（谁验收）
```

同时问：**这个流程上次出问题，卡在哪里？**

如果用户描述不清楚，帮他建一个通用框架：

```
需求类流程：提出 → 评估 → 设计 → 执行 → 验收 → 上线 → 复盘
决策类流程：信息收集 → 方案设计 → 评审 → 拍板 → 传达 → 执行
客户类流程：获取 → 转化 → 交付 → 维护 → 扩展
```

---

### Step 2：节点画像

对每个关键节点建立画像：

```
[节点名称]

输入条件：
  需要什么才能开始执行（信息/决策/资源/上游完成状态）
  当前实际收到的是什么（和需要的差距在哪）

执行主体：
  谁执行（职能/角色）
  执行权限边界（能自主决定什么，需要上报什么）

完成标准：
  什么状态算「做完了」（当前是否有明确定义）
  谁来验证完成（和执行主体是同一人？）

交出去的东西：
  输出给谁
  交接协议是否明确

风险评级：
  高（断过/可能断/一断全卡）
  中（偶尔有摩擦但能过）
  低（基本稳定）
```

---

### Step 3：断裂点诊断

对每个高风险节点，匹配断裂类型（五类中的哪一个或几个），输出：

```
[节点名] × [断裂类型]

根本原因：
  不是「这个人没做好」，而是 [系统性原因]

历史证据：
  这个断裂出现过几次，每次是什么情况

影响范围：
  这个节点断裂后，会影响哪些下游节点

修复方案：
  最小成本修复：不改变流程结构，只加一个确认机制 / 明确一个标准 / 指定一个人
  根本修复：重新设计这个节点的输入条件 / 交接协议 / 决策权分配
  绕过方案：在修复完成之前，用什么临时机制降低断裂频率
```

---

### Step 4：输出流程健康报告

```
[流程名称] 健康报告

总体评级：健康 / 有风险 / 高风险

高风险节点（必须优先处理）：
1. [节点名] — [断裂类型] — [修复方案]
2. ...

中风险节点（建议处理）：
...

关键路径：
  从起点到终点，哪几个节点是不能绕过的关键路径
  关键路径上有几个高风险节点

优化优先级：
  第一步（本周）：解决 [具体节点] 的 [具体问题]，方法是 [具体操作]
  第二步（本月）：……
  第三步（本季）：……

不建议做的：
  XX 看起来能解决问题，但实际上只是把断点从 A 移到 B
```

## 质量标准

| 层级 | 不合格 | 合格 |
|------|--------|------|
| 断裂诊断 | 「这个流程需要优化」 | 「需求评审节点属于'输入不完整'类型：工程收到的需求文档缺少错误态设计，导致每次都要拉回 PM 确认，平均延迟 2 天」 |
| 修复方案 | 「加强沟通」 | 「在需求文档模板里增加强制字段：错误态设计、边界情况说明，PM 不填不能进入评审，交接协议明确」 |
| 优先级 | 「所有节点都需要改进」 | 「关键路径上的审批节点是最高优先级：这是唯一瓶颈，审批人在审 8 个项目，建议把日常决策权下放，只保留超过 XX 预算的审批」 |

**没有指出「在哪个节点断、断裂原因是系统还是人、怎么修复」的诊断，是废话。**

## 反模式声明

### 失败 1：把流程问题归因于「人的问题」而不是「节点问题」
用户说「这个流程总是卡在张三那里」，模型就分析张三的能力和态度，不追问「换了李四是不是也会卡」。同一个位置换不同人还出同样的问题，是节点问题。
**纠正**：诊断前先做替换测试——「这个位置换过人吗？换了人问题消失了吗？」如果换人问题还在，一定是节点问题，不要分析人。

### 失败 2：给「加强沟通」这种笼统建议，不识别具体断裂类型
用户说「我们部门之间总是沟通不畅」，模型输出「建议加强跨部门沟通机制」，不断裂类型（输入不完整？交接协议缺失？决策权模糊？反馈回路断裂？）。
**纠正**：必须先匹配五类断裂类型中的具体一种，再给对应修复方案。不同类型的断裂，修复方式完全不同。

### 失败 3：跳过流程速写直接给诊断
用户说「流程有问题」，模型就直接输出「你的审批流程需要优化」，不问流程的完整路径、每个节点是什么、上次卡在哪里。
**纠正**：即使只有 5 分钟，也要先画流程速写（起点→节点→终点），再定位卡点。没有流程图的诊断是猜的。

## 与 create 生态的协作

| 场景 | 路径 |
|------|------|
| 流程诊断完，需要改变相关人的行为 | `zaoren-process` → `zaoren-leader`（如何推动流程改变）|
| 流程诊断完，需要判断改变是否值得投入 | `zaoren-process` → `zaoren-drucker`（有效性判断：该不该做）|
| 流程里某个关键人物是瓶颈 | `zaoren-process`（节点诊断）+ `zaoren`（造这个人的判断系统）|
| 修复了流程，想固化成标准 | `zaoren-process` → `taxue-build`（沉淀成可复用 skill）|

## 快速启动

```
用户：「我们的 [流程名] 总是在 [某个地方] 出问题」
→ 直接进 Step 2，只画这个卡点前后的 3 个节点，不需要全流程
→ 识别断裂类型，输出最小成本修复方案

用户：「帮我诊断一下我们的整个 [流程名]」
→ 进 Step 1 做流程速写，识别所有节点
→ 重点在高风险节点，中低风险节点简单带过
```

先找最高风险的那一个节点，修好它，比把所有节点改一遍更有价值。
